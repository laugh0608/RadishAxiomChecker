# Checker 开发目标与验收计划

更新日期：2026-09-05

状态：开发规划；不修改已冻结语义、公共格式、支持集合或上游 ADR。

用途：把独立复核能力转化为可审阅的验收目标。读者为 Checker 与主仓的语义、实现、测试及运行维护者。本页不承载当前完成状态、逐日记录或外部操作授权；当前顺位见[当前状态](status/current.md)。

## 目标与架构原则

Checker 的目标是依据明确规范，独立检查生产 Evidence 的主张与支撑材料，并使接受范围、缺口和信任可追溯。应分别度量具体输入 / 反例 / 输出复核、attestation 绑定审计与正向独立证明，不能把构建、CLI 或安装成功累计为证明能力。

保留目前字节与协议、IR 语义、Evidence、结果和交付的包边界，继续共享 Checker 自有有限解释器。抽象或拆包须有实际重复或边界问题作为依据。与生产端的独立性覆盖解析、义务生成、解释和测试期望，不以换用另一种语言代替独立推导。

能力扩展逐项记录规范版本、构造 / 规则、解析与类型检查、具体执行、反例复核、独立证明、失败行为以及测试入口。同一个构造在不同列的支持可以不同；矩阵不另造协议状态或默认成功路径。

## 一、反例目标归因

要解除的不确定性是：已重放的有限失败是否反驳当前义务，而非只说明程序别处存在错误。当前疑点与代码依据见状态页。

验收材料必须包含：

1. 每种 target 的义务含义、subject 及必要的契约 / 数据关系，明确对应的可计算违反谓词。
2. 目标确实违反、目标成立、另一个义务违反三种情况；覆盖 `row-coverage`、`field-origin`、`group-conservation`，并保留直接契约和键基数的对照。
3. 身份全部有效的完整 bundle：重算受影响 definition、document、制品、manifest / request 等绑定，使反例能到达目标判断；不能只触发旧摘要拒绝。
4. 对测试实际抵达的检查层、观察结果和预期的记录；如发现错误接受，先保留能暴露问题的回归，再修实现并重跑锁定场景。

行覆盖要回答“哪些行按哪个关系必须保留”；字段来源要明确接口、表达式作用域、传递或控制依赖，区分语法引用与语义来源；分组守恒要绑定目标前驱、声明键和聚合关系。生产者提供的 `requiredFields` / `requiredKeys` 只能作为待核对见证，不能自行定义目标真假。

若反例不能复现，保留有效区分测试和排除原因；若规范不能唯一决定期望，先提交精确的语义问题与兼容性影响，不凭实现经验补一个隐式规则。完成标准是每个已支持 target 都有明确依据及上述区分测试，而非仅增加测试数量。

## 二、同域泛化与能力声明

在既有首域和已支持运算内设计一道独立合成新题，附接口改名及节点组合变体；任务语义和预期由独立审阅给出，不调用生产 helper 生成唯一期望。

先标明各变体在哪一层被接受或拒绝，尤其检查 `lockedBenchmarkID` 按接口名称识别题目的约束。区分“语义运算已实现”“输入数据格式可表达”“完整 invocation 可消费”三个事实，不为通过新题绕过 decoder 或身份检查。

需要解除名称耦合时，先提出版本化的数据与 IR 接口绑定方案；将实验题目身份与语义求值所需输入区别建模，保留旧 profile 精确行为及新旧版本拒绝 / 兼容测试。不能默认为任意名称或未知 benchmark 提供 fallback。

完成标准是新题和各变体通过同一生产检查路径，错误候选被拒绝或其失败被正确复核，范围外构造按现有协议显式失败，能力矩阵能逐项追到实现与验证。新材料独立留存，不改写四题锁定 fixture 或正式 Agent 实验的样本与评分；扩大正式实验需新版本注册。

## 三、首条完整正向证明链

先选择规范足够明确且规则集小的一种义务，给出完整信任分析和验收方案，再实施。可评估结构性纯效果规则等候选，但本计划不宣布任何规则已进入支持集合。

独立验收须闭合：

- 从绑定 IR 和 profile 重建目标义务；
- 独立确定待证明命题与逻辑编码，验证生产查询与目标的关系；
- 用已声明规则 / certificate 路径检查证明及全部 side condition；
- 明示仍受信任的前提、工具、规则解释器和未覆盖范围。

负例至少包括：有效证明对应错误命题、目标或假设被替换、遗漏必要条件、未知规则、hole / trust step、伪造状态、截断材料与资源耗尽。验证证书格式或确认 `unsat` 不能替代命题绑定。

完成标准是至少一种规则在完整调用中产生可追溯的独立覆盖，错误命题或材料不能被接受；其他义务仍按实际能力保留缺口或 trust。支持集合与公共契约扩展单独审阅，不把有限世界测试升级为全输入证明。

## 四、结果解释与外层保证

沿用现有四态和程序结论，首先通过既有结果及其引用制品改善解释，不立即修改 companion 格式。消费者应能回答：

| 问题 | 验收要求 |
| --- | --- |
| 接受的是什么 | 同时显示 Evidence 的程序结论和独立接受结果；正确报告 `violated` 不显示为程序正确 |
| 检查了哪些义务 | 分列已复核的有限事实、独立 proof、attestation 和材料缺口，保留 ID / ref / 版本 |
| 还有哪些未知 | 决定性失败分支未依赖的 proof 缺口仍可见，不将内存 finding 丢失误解为无缺口 |
| 命令是否完成 | `0` 只表示完整结果已输出；结果拒绝、incomplete 与外层 `not-produced` 分别处理 |
| 隔离保证来自哪里 | 分列 Checker 内部报告、launcher 配置与运行观察、qualification 和 host / runner / guest TCB；不让自报 `passed` 证明 OS hard isolation |

如果现行格式无法保留所需逐义务信息，先提出可审阅的版本化诊断或结果迁移，明确身份、引用、缺失行为和兼容性；不得往闭合 JCS 临时加字段或另造一套判定器。端到端验收包括程序违规被接受、证明材料不足、允许信任、前置拒绝与进程无结果，确认不会展示相反或过强结论。

## 五、测试、资源与可信基

语义变异应同时覆盖局部 API 和完整 invocation；摘要篡改测试与摘要有效的语义欺骗测试分别统计。小规模有限输入穷举、保留新题、独立性质断言和运算组合用于发现共同误解；重复执行仅证明确定性，不能替代这些正确性检查。测试材料与期望生成器必须有独立依据和可复现入口。

按改动风险逐步补充严格字节入口的模糊测试，以及深度、字符串 / 整数长度、表容量、join scan、group 和 paired-world 规模边界。记录抵达层级、返回状态、消耗和终止行为，不只统计无崩溃。

真实负载矩阵区分 semantic steps / logical bytes、实际 Go heap / RSS、host footprint、冷启动与 deadline；内部计量不是外层硬限制。与主仓一起审阅全生命周期、取消、输出上限与异常 teardown，执行仍须满足工具来源、隔离和授权前置。

维护运行时实际依赖与 TCB 视图，分别列源码快照、构建器、分发工具和运行时组件；不因同仓而把所有包认定为运行可信基，也不遗漏实际链接依赖。若将来拆分文档 / 全源码出处与运行语义身份，须新版本设计；当前所有文档仍进入 `checker.source`，不得增加隐式排除。

## 跨仓交接与完成记录

Checker 负责独立实现与自身验证；[RadishAxiom 主仓](https://github.com/laugh0608/RadishAxiom)负责公共语义 / 协议决策、生产管线、launcher 与登记。跨仓只交换按精确来源和摘要导入的规范 / fixture，不共享生产实现；导航链接不构成运行依赖。

每个切片交接应记录变更语义与身份、验证的精确版本、实际 / 未运行检查、反例或证明覆盖分母、剩余 trust、工作区和提交状态。生成源码身份不触发 payload 重建或旧登记重绑；源码变化后的新 artifact 必须重新走对应验收。

规划可独立推进必要设计和合成材料准备，但不授权依赖安装、产品进程、远程操作、发布或激活。公共语义、格式、资源和隔离变化按主仓对应 ADR 决策；当前 v0.1 / v0.2 边界继续遵守 ADR 0009。
